# 调度任务部分成功与失败明细设计

## 背景与目标

GateRank 管理后台当前把调度任务记录为 `running`、`succeeded` 或 `failed`。稳定性采集、订阅节点更新、性能采集、风险体检和稳定性复测保护都是批量任务，但现有实现只要一个机场失败，就把整次执行显示为“失败”。例如 `60/61 succeeded, 1 failed` 与 `0/61 succeeded, 61 failed` 在页面上具有相同状态，管理员无法快速区分轻微局部故障和整批故障。

本次改造需要在不削弱失败告警的前提下，让管理后台明确显示一次任务处理了多少目标、成功多少、失败多少，并允许查看所有已保存的失败机场及原因。历史记录也需要尽可能自动识别；系统不能伪造旧记录中从未落库的失败明细。

## 核心决策

### 持久化状态与展示结果分离

数据库中的 `admin_scheduler_runs.status` 继续使用：

```text
running | succeeded | failed
```

只要批量任务包含失败项，持久化状态仍为 `failed`，以保持现有监控、统计、筛选和自动化语义。API 在返回运行记录时增加派生的展示结果：

```text
running | succeeded | partial | failed
```

派生规则固定为：

- 任务仍在运行：`running`。
- `success_count > 0` 且 `failure_count > 0`：`partial`。
- `success_count > 0` 且 `failure_count = 0`：`succeeded`。
- `success_count = 0` 且 `failure_count > 0`：`failed`。
- 非批量任务或无法可靠提取数量的记录：沿用持久化状态。

这样不会为数据库 ENUM 增加迁移风险，也不会把部分失败从现有失败告警中移除。管理后台将 `partial` 显示为“部分成功”，使用克制的琥珀色语义。

### 标准化批量执行结果

API 中每条调度运行记录增加可选的标准化结果：

```text
outcome: running | succeeded | partial | failed
result_summary:
  total_count: number
  success_count: number
  failure_count: number
  skipped_count: number | null
  failures:
    - airport_id: number | null
      airport_name: string | null
      error: string
```

`result_summary` 是对不同任务 `detail_json` 的统一读取视图，不替换原始 `detail_json`。后端负责归一化，前端不得自行解析中文 `message` 作为主要数据来源。

新执行记录必须在 `detail_json` 中保存结构化数量和完整失败数组。错误原因在落库和返回前继续脱敏：订阅 URL、令牌和其他敏感地址不得出现在管理后台。

不同任务的数量映射必须明确，不能用一个含义不一致的字段代替：

- 稳定性采集、性能采集：`total_count = airport_count`。
- 订阅节点更新：`total_count = airport_count`，并单独返回 `skipped_count`；满足 `total_count = success_count + failure_count + skipped_count`。
- 风险体检：`total_count` 为实际进入检查循环的机场数。
- 稳定性复测保护：`total_count = flagged_count`，`success_count = retested_count`，`failure_count = failures.length`；`checked_count` 继续作为原始明细保留，但不冒充处理总数。

## 任务覆盖范围

本次标准化覆盖具有机场级处理结果的任务：

- 稳定性采集
- 订阅节点更新
- 性能采集
- 风险体检
- 稳定性复测保护

聚合重算和欠费上架同步继续沿用任务级成功或失败语义；如果它们没有机场级失败数组，不显示空的“查看失败详情”入口。

### 新记录

稳定性采集和性能采集需要保留脚本输出中的：

- `airport_count`
- `success_count`
- `failure_count`
- `failures`

订阅节点更新已保存上述数据和完整失败数组，继续复用现有结构。风险体检需要在逐机场执行时收集失败机场 ID、名称和脱敏后的异常原因。稳定性复测保护继续使用现有 `failures`，并从触发、成功复测和失败数量推导结果。

### 历史记录

历史记录按以下优先级推导：

1. 优先读取结构化 `detail_json`。
2. 如果旧稳定性或性能记录只有 `summary` / `message`，从固定英文计数格式中提取 `60/61 succeeded, 1 failed`。
3. 只展示历史记录实际保存的失败项。

旧稳定性记录只保留了第一个失败机场时，页面需要明确展示该已知项，但不得声称它是完整列表。如果计数表明有更多失败项，显示“另有 N 个历史失败项未保存明细”。

## API 与数据流

调度运行记录仍由 `SchedulerRunRepository` 读取原始数据库字段。服务层在返回任务列表、执行日志和每日统计所需的最新执行记录前，调用统一归一化函数生成 `outcome` 和 `result_summary`。每日统计查询需要同时返回最后一次运行的 `message` 和 `detail_json`，再附加 `last_outcome` 与 `last_result_summary`，不能只依据 `last_status` 猜测处理数量。

数据流如下：

```text
Python/服务任务执行
  -> 原始 detail_json 与 failed 状态落库
  -> 服务层归一化批量数量和失败项
  -> API 返回 outcome + result_summary
  -> 管理后台统一渲染状态、数量和失败详情
```

归一化逻辑必须是独立、可单元测试的纯函数，避免任务列表、执行日志和以后其他消费者各写一套判断规则。

## 管理后台信息架构

视觉基调保持当前 GateRank Admin 的白色/浅灰表面和中性文字。成功使用绿色，部分成功使用琥珀色，完全失败使用红色；颜色之外同时提供明确文本，不能只依赖颜色传达状态。

### 任务卡片

“最近一次执行”区域显示：

```text
部分成功 / 定时触发 / 2026/08/05 04:00
总数 61 · 成功 60 · 失败 1
```

有失败项时提供“查看 1 个失败项”的原生可展开控件。展开后逐条显示机场名称、`#ID` 和原因。

### 每日调度统计

现有“成功”和“失败”表示执行次数，不是机场数量，因此列名调整为：

```text
成功执行 | 失败执行
```

增加“最近处理结果”列，显示最近一次运行的：

```text
成功 60 · 失败 1
```

如果最近一次运行不是批量任务或没有可靠数量，则显示 `-`。最后状态列使用派生展示结果，因此可以显示“部分成功”。

### 执行日志

状态列使用带文字的语义标签。结果列分两层：

1. 首行显示 `总数 61 · 成功 60 · 失败 1`。
2. 次行保留简短任务消息。

当失败项存在时，提供“查看 N 个失败项”展开入口。每个失败项展示：

- 机场名称；未知名称时显示 `机场 #ID`。
- 机场 ID（如有）。
- 脱敏后的原始失败原因。

原生 `<details>` / `<summary>` 作为默认交互，保留键盘可操作性，不引入弹窗和额外全局状态。

### 状态筛选

数据库仍把部分成功保存为 `failed`，因此现有筛选项“失败”改名为“失败/部分成功”。筛选行为保持不变，避免新增分页语义不一致的前端过滤。

## 异常与安全处理

- 计数缺失、非数字或相互矛盾时，不推导部分成功，沿用原始状态。
- `total_count` 与 `success_count + failure_count + skipped_count` 不一致时视为无效汇总；不适用跳过语义的任务把 `skipped_count` 按 0 处理。
- 单条错误原因必须经过现有 URL 脱敏逻辑，并设置合理长度上限。
- 失败项数组不存在时不渲染展开入口。
- 历史计数大于已保存失败项数量时，明确提示明细不完整。
- 前端只渲染文本，不使用 HTML 注入错误内容。

## 测试与验收

### 后端归一化

- `60/61 succeeded, 1 failed` 归一化为 `partial`，数量为 61、60、1。
- `61/61 succeeded, 0 failed` 归一化为 `succeeded`。
- `0/61 succeeded, 61 failed` 归一化为 `failed`。
- 订阅节点更新的结构化 57 成功、4 失败返回全部 4 个失败项。
- 稳定性复测保护的 2 成功、1 失败归一化为 `partial`。
- 历史记录只有第一个失败项时返回缺失明细数量。
- URL 和令牌不会出现在归一化错误文本中。
- 非批量任务继续沿用原始状态。

### 执行器

- 新稳定性和性能执行记录保留完整 `failures` 数组。
- 风险体检保留所有失败机场和原因。
- 订阅更新继续保留全部失败机场。
- 任一失败项仍使持久化状态为 `failed`。

### 管理后台

- 最近执行卡片显示“部分成功”和准确数量。
- 每日统计明确区分执行次数与机场处理数量。
- 执行日志可展开并查看所有已保存的失败机场。
- 历史明细不完整时显示提示，不伪造机场名称。
- “失败/部分成功”筛选仍能看到两类记录。
- 成功、部分成功、完全失败和无汇总四种状态在桌面与移动端均清晰可读。

### 验收示例

对于以下运行：

```text
稳定性采集：总数 61，成功 60，失败 1
失败：网际快车 #43 — The read operation timed out
```

后台必须显示：

```text
状态：部分成功
结果：总数 61 · 成功 60 · 失败 1
失败详情：网际快车 #43 — The read operation timed out
```

数据库中的该运行状态仍为 `failed`，现有失败监控继续生效。

## 不在本次范围

- 不修改任务调度时间或启停状态。
- 不重跑历史任务。
- 不修复具体机场的订阅地址或外站超时。
- 不把部分成功从失败告警中排除。
- 不迁移 `admin_scheduler_runs.status` ENUM。
- 不尝试恢复旧记录中从未保存的失败机场。
