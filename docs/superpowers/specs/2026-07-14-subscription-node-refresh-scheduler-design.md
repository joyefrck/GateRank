# 订阅节点定时更新设计

## 背景

GateRank 的性能测试已经改为只读取 `airport_subscription_node_snapshots` 中已保存的订阅节点快照，不会在性能测试开始时临时刷新订阅。为了让凌晨 4 点左右的性能测试使用当天最新节点，需要在性能测试前独立执行一次批量订阅更新。

仓库已经提供 `scripts/capture_subscription_nodes.py`，它可以拉取订阅、规范化内容、解析支持的节点，并通过后台接口保存节点快照。本次需求只为这条既有链路增加可管理的每日调度，不重复实现订阅解析或快照持久化。

## 目标

- 在后台“任务调度”页面新增独立的“订阅节点更新”任务。
- 新任务默认开启，每天按 `Asia/Shanghai` 时区在 `01:00` 执行。
- 刷新性能测试会处理的可运行机场中所有已配置的订阅链接，并保存最新节点快照。
- 确保后续性能测试继续只读取已保存快照，且能够取得凌晨 1 点任务成功写入的最新快照。
- 保留现有任务统一的启停、修改时间、立即重载执行、执行记录和每日统计能力。

## 非目标

- 不修改性能探测、节点选择、测速或评分算法。
- 不在性能测试任务开始时再次刷新订阅。
- 不新增节点快照表或新的订阅解析实现。
- 不刷新已下线或不公开、因而不会进入性能测试的机场。
- 不把没有配置订阅链接的机场计为刷新失败。

## 方案选择

采用独立调度任务 `subscription_node_refresh`，由现有 `AdminSchedulerService` 管理，由 `SchedulerTaskExecutor` 调用 `scripts/capture_subscription_nodes.py`。

没有采用以下方案：

- 合并进性能测试任务：订阅刷新失败会扩大性能任务的故障边界，并减少刷新与测速之间的缓冲时间。
- 使用服务器外部 Cron：无法在 GateRank 后台统一启停、重载、查看日志或统计。

## 调度配置

新增任务定义：

- `task_key`: `subscription_node_refresh`
- 名称：`订阅节点更新`
- 默认状态：开启
- 默认时间：`01:00`
- 时区：`Asia/Shanghai`
- 描述：`批量刷新性能测试范围内的订阅链接并保存最新节点快照，供后续性能采集使用。`

新任务的默认开启状态不依赖 `NIGHTLY_PIPELINE_ENABLED`。首次部署并执行调度表结构初始化时，新记录以 `enabled = 1` 写入。已经存在的其他任务保持原有启用状态和默认逻辑不变。

## 执行流程

1. 调度器在北京时间 `01:00` 创建 `admin_scheduler_runs` 运行记录。
2. 执行器运行 `scripts/capture_subscription_nodes.py`，注入：
   - `ALL_AIRPORTS=1`
   - `SOURCE=scheduler-subscription-node-refresh`
   - 后台 API 鉴权信息
   - 与现有批量性能任务一致的可选 `AIRPORT_STATUS`
3. 脚本分页取得机场，沿用性能任务的可运行范围：跳过 `status=down` 或 `is_listed=false` 的机场。
4. 批量模式下跳过没有 `subscription_url` 的机场，并在汇总中记录跳过数量；单机场手动抓取仍保留现有的缺少订阅链接错误。
5. 对每个已配置订阅链接的机场依次拉取订阅。优先使用 Clash Meta User-Agent，失败或内容不可用时使用 GateRank 默认 User-Agent 重试。
6. 解析成功后调用现有快照写入接口，将节点保存至 `airport_subscription_node_snapshots`。
7. 所有机场处理结束后输出 JSON 汇总，调度执行器将其转换为任务状态、消息和详情。
8. 凌晨性能测试按机场读取最新快照，同时继续校验快照中的订阅 URL 与机场当前订阅 URL 一致。

## 成功与失败语义

- 全部有订阅链接的目标机场刷新成功：任务状态为 `succeeded`。
- 单个机场失败：继续处理后续机场，保留此前成功写入的快照；最终任务状态为 `failed`。
- 没有配置订阅链接的机场：计入 `skipped_count`，不计入失败。
- 没有任何符合条件的订阅链接：任务正常完成，消息明确显示目标数为 0。
- 缺少后台 API 鉴权：任务失败，不启动脚本。
- 脚本超时或进程异常：任务失败，并复用现有安全摘要逻辑展示错误。

执行消息至少包含：目标订阅数、成功数、失败数和跳过数。详情 JSON 保留各机场 ID、名称及脱敏后的错误摘要，不写入或展示完整订阅 URL。

## 数据库与类型变更

以下位置增加 `subscription_node_refresh`：

- `SchedulerTaskKey` 后端联合类型。
- `admin_scheduler_tasks.task_key` 和 `admin_scheduler_runs.task_key` 的 MySQL 枚举。
- 运行记录仓库的任务顺序和初始结果映射。
- `backend/sql/schema.sql` 的安装基线。
- 后台路由的任务键校验。
- 管理端的 `SchedulerTaskKey`、标签格式化和统计筛选项。

数据库初始化仍使用现有 `ensureSchema()` 扩展枚举并插入缺失的默认任务记录，不单独引入迁移框架。

## 后台界面

任务列表自动渲染新任务卡片，沿用现有卡片和交互：

- 显示“已开启”、每日执行时间、下次执行、调度状态和最近一次执行。
- 可以关闭或重新开启。
- 可以修改每日执行时间。
- “重启调度器”会立即真实执行一次订阅节点更新。
- 每日调度统计和运行记录可以按“订阅节点更新”筛选。

页面说明改为涵盖订阅节点更新等全部后台任务，不再写死为四个全局任务。

## 测试与验证

后端回归测试覆盖：

- 任务表和运行表枚举包含新任务键。
- 默认任务种子包含 `01:00`、默认开启的 `subscription_node_refresh`，且其他任务默认逻辑不变。
- 执行器为新任务调用正确脚本并注入 `ALL_AIRPORTS`、`SOURCE`、鉴权和机场状态环境变量。
- 脚本成功、部分失败、无订阅跳过和超时能够生成正确状态与安全摘要。
- 后台路由接受新任务键并继续拒绝未知任务键。

Python 回归测试覆盖：

- 批量抓取跳过无订阅机场。
- 单机场抓取缺少订阅链接仍报错。
- 部分机场失败后其余机场继续执行，成功快照仍被保存。
- 输出汇总不泄露完整订阅 URL。

前端验证覆盖：

- TypeScript 类型检查通过。
- 新任务标签和统计筛选项正确显示。
- 任务调度页面构建成功。

最终运行相关的后端测试、Python 测试、前端类型检查和生产构建，并检查 Git 差异只包含本需求范围内的文件。

## 验收标准

- 部署后后台任务列表出现默认开启的“订阅节点更新”，默认时间为 `01:00`。
- 手动点击“重启调度器”能够刷新所有符合条件的订阅链接并写入新快照。
- 任务卡片和运行记录显示目标数、成功数、失败数和跳过数。
- 某个订阅失败不会阻止其他机场保存新快照，但本次调度记录为失败。
- 性能测试读取最新且订阅 URL 匹配的已保存快照，不发起订阅刷新。
- 日志、后台消息和运行详情不暴露完整订阅链接。
