# 调度任务混合结果准确展示设计

## 背景与目标

GateRank 已经支持把批量运行派生为 `partial`（部分成功），但 2026-08-13 的生产记录暴露出两个结构化汇总缺口：

- 网络覆盖实际为 63 个机场中成功 58、失败 3、跳过 2，但执行器丢弃了脚本的 `skipped_count`，导致校验得到 `58 + 3 != 63`，页面无法派生部分成功，只能沿用数据库中的 `failed`。
- 性能采集的中心脚本实际成功 2、失败 0，其余机场未进入旧中心采集；区域阶段成功创建 118 个任务，但 2 个机场因缺少节点快照未能派发。现有汇总没有表达区域派发的机场级成功、失败和跳过语义，页面同样只能显示任务级失败。

本次改造要让后台返回并展示实际混合结果，同时保持数据库失败告警语义，不重跑历史任务、不修改生产采集数据，也不把局部失败伪装为完全成功。

## 核心决策

### 保持持久化状态与展示结果分离

`admin_scheduler_runs.status` 继续使用 `running | succeeded | failed`。只要一个实际处理阶段存在失败项，持久化状态仍可为 `failed`；API 使用已有的派生展示状态 `running | succeeded | partial | failed`。

展示规则保持：

- 有有效成功结果且有失败结果：`partial`。
- 有有效成功结果且没有失败结果：`succeeded`。
- 没有有效成功结果且存在失败，或任务本身崩溃、鉴权失败、整体超时：`failed`。
- 计数缺失或矛盾：不猜测，沿用持久化状态。

### 网络覆盖保留完整脚本汇总

通用脚本汇总解析器增加 `skipped_count`，默认值为 0，并允许失败项使用脚本当前返回的 `error_code` 作为安全错误文本。网络覆盖的新执行记录在 `detail_json` 中保留：

```text
airport_count
success_count
failure_count
skipped_count
failures[]
```

归一化器对网络覆盖读取 `skipped_count`。2026-08-13 的历史记录虽然 `detail_json` 中没有跳过数，但原始 `stdout` 没有落库，因此不能凭空恢复；新记录必须准确显示 `58/63 succeeded, 3 failed, 2 skipped`。对于已有历史记录，可在汇总文本明确包含 skipped 数时解析；否则继续沿用原始状态。

### 性能中心采集与区域派发分层表达

性能执行记录保留两个互不混淆的结果层：

1. `central_collection`：旧中心采集脚本返回的机场总数、成功、失败、跳过。
2. `regional_dispatch`：区域性能任务按机场统计的目标、成功派发、失败派发、跳过，以及创建的任务数量。

`PerformanceProbeDispatchResult` 增加机场级计数：

```text
airport_count
success_count
failure_count
skipped_count
created
official
shadow
failures[]
```

机场具有已启用的大陆探针且至少创建或命中当日幂等任务时计为区域派发成功；没有启用的大陆探针计为跳过；缺少快照、选中节点为空或派发异常计为失败。实现必须区分“幂等任务已经存在”和“没有可派发任务”，不能把重复调度误报为跳过或失败。

性能任务的顶层展示汇总以区域派发的机场级结果为主，因为它代表当前正式大陆性能采集范围；中心采集结果继续在明细中单独展示。只要区域成功派发机场数大于 0 且失败数大于 0，展示为“部分成功”。如果没有区域目标，则退回中心采集汇总。

调度记录只表示派发时的实际结果，不伪装成异步区域任务的最终采集完成情况。页面文案必须使用“区域派发”或“区域任务已排队”，不能写成“区域采集成功”。

## 数据流与组件边界

```text
Python 脚本汇总
  -> SchedulerTaskExecutor 保存完整中心计数
PerformanceProbeDispatchService 按机场派发
  -> 保存区域机场计数、任务数和失败项
SchedulerRunPresentation
  -> 选择适用的主展示汇总并派生 partial
Admin UI
  -> 显示主汇总，并补充中心采集/区域派发明细
```

职责保持清晰：派发服务只产生事实计数；执行器组合阶段结果；展示归一化器只校验和选择汇总；前端不从中文消息猜测业务状态。

## 后台展示

沿用现有 GateRank Admin 的状态标签与结果组件，不新增视觉原语：

- `partial` 继续使用琥珀色“部分成功”。
- 主结果显示 `总数 / 成功 / 失败 / 跳过`。
- 性能任务增加一行克制的补充文字，例如 `中心采集：成功 2，失败 0；区域任务：排队 118，派发失败机场 2`。
- 网络覆盖失败详情展示机场、ID 和安全错误码。
- 只有实际保存了失败项时才显示可展开详情；缺失详情数量继续使用已有提示。

视觉目标是让管理员先看到任务整体是否产生有效结果，再看到局部失败规模和具体原因；不改变页面布局、导航或交互模式。

## 异常与兼容性

- `total = success + failure + skipped` 是任何机场级汇总生效的前提。
- 区域任务创建数不是机场成功数；两个值必须分别保存。
- 异步任务稍后失败不回写本次调度运行状态，本次只准确描述派发结果。
- 失败文本继续经过 URL 脱敏和长度限制，不返回订阅地址、节点配置或令牌。
- 旧记录只使用已落库事实；无法恢复的跳过数不猜测、不回填数据库。
- 聚合重算、风险体检、稳定性采集和订阅更新的既有展示语义不变。

## 测试与验收

### 执行器与派发服务

- 网络覆盖 `58 success / 3 failure / 2 skipped / total 63` 被完整保存。
- 网络覆盖失败项只有 `error_code` 时仍返回安全失败详情。
- 性能中心采集成功且区域 59 个机场派发成功、2 个失败时，持久化状态保持 `failed`，展示所需区域汇总为 `59 success / 2 failure`。
- 区域没有启用探针的机场计为跳过。
- 幂等重跑不会把已经存在的任务误报成失败。
- 区域全部派发失败且没有有效中心结果时保持完全失败。

### 归一化与 UI

- 合法的网络覆盖混合结果派生为 `partial` 并显示 58、3、2。
- 合法的性能区域混合结果派生为 `partial`，主汇总使用机场数而不是任务数。
- 性能补充明细明确区分“中心采集”和“区域派发”。
- 矛盾计数不派生部分成功。
- 成功、部分成功、完全失败及旧记录无可靠汇总四类状态保持兼容。

### 生产验收

部署后只读检查下一次执行记录：

- API `/healthz` 正常。
- `admin_scheduler_runs.detail_json` 包含完整网络覆盖跳过数或性能区域机场计数。
- 管理后台网络覆盖和性能行在存在有效结果与局部失败时显示“部分成功”。
- 页面结果数量与数据库结构化详情一致。

## 不在本次范围

- 不修复具体机场的订阅地址或节点可用性。
- 不改变采集调度时间、探针测速算法或聚合评分规则。
- 不等待区域异步采集全部完成后再结束调度运行。
- 不迁移数据库状态 ENUM。
- 不修改或回填历史生产记录。
