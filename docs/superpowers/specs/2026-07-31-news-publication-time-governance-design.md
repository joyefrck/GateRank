# News 发布时间统一治理设计

## 背景与现状

生产环境当前共有 43 篇已发布 News。公开 API 的日期分布为：

- 2026-07-30：8 篇；
- 2026-07-05：15 篇；
- 2026-06-06：10 篇；
- 2026-06-02、2026-05-29、2026-05-25：各 1 篇；
- 2026-05-21：7 篇。

所以数据库并非所有文章都发布于 7 月 30 日。不过 News 首页会在主打、推荐、
分类侧栏和普通列表中重复展示同一批最新文章，导致 7 月 30 日在首屏密集出现。

更根本的问题在写入端：现有发布服务每次执行 `publish` 都把
`published_at` 覆盖为当前上海时间。已经发布的文章只要再次点击“发布文章”，原始
发布日期就会丢失。与此同时，文章浏览量自增也会触发
`updated_at ON UPDATE CURRENT_TIMESTAMP`，因此当前 `updated_at` 不能可靠代表
内容更新时间。

## 目标

- `published_at` 始终代表首次正式发布时间，普通编辑和恢复上线不再修改它。
- `updated_at` 代表编辑产生的最后内容或运营元数据更新时间，不受浏览量影响。
- 首页、News 列表、分类页、专题页、详情页、结构化数据和 Sitemap 使用一致的
  时间语义。
- 修复可以确认来源的历史错误日期，并为每次生产更新保留可回滚证据。
- 减少同一文章在 News 页面多个区块中的重复展示，避免少量同日文章占满首屏。
- 不修改文章内容、Slug、浏览量、分类、专题和推荐配置。

## 方案比较

### 方案一：只保护 `published_at`

将发布写入改为 `current.published_at || now`，再手工修改 7 月 30 日的文章。
改动最小，但不会处理被浏览量污染的 `updated_at`、SEO 时间字段和页面重复展示，
只能解决最明显的症状。

### 方案二：统一时间治理与受控修复（采用）

保持现有表结构，以不可变 `published_at` 和可编辑 `updated_at` 分离首次发布与
后续更新；阻止浏览量刷新 `updated_at`；统一所有公开出口；通过 dry-run 映射和
事务脚本修复历史数据；同时对 News 页面做展示去重。

该方案覆盖根因且不引入文章版本系统，改动和风险可控。

### 方案三：完整文章修订历史

新增修订表、首次发布事件和每次重新发布事件。审计能力最完整，但需要编辑器、
API、数据库和恢复流程的较大改造，超出本次日期治理所需范围。

## 时间字段语义

### `published_at`

- 草稿首次发布时写入当前上海时间。
- 已发布文章保存更新时保持原值。
- 已下线文章恢复发布时保持原值。
- 本次不提供“作为新内容重新发布并刷新排序”的功能。未来如有需要，必须设计
  独立操作和明确确认，不能复用普通发布接口。

发布服务使用以下语义：

```ts
published_at: current.published_at || nowInShanghai()
```

### `updated_at`

- 编辑标题、正文、摘要、封面、分类、专题、推荐状态等运营内容时正常更新。
- 浏览量自增必须显式保持原值，例如：

```sql
UPDATE news_articles
SET view_count = view_count + 1,
    updated_at = updated_at
WHERE id = ?;
```

- 历史数据恢复时，如果无法从可靠备份找回真实更新时间，则使用修复后的
  `published_at` 作为保守基线，避免把访问时间伪装为内容修改时间。

## 后台编辑流程

根据文章状态显示明确操作：

- 草稿：`保存草稿`、`发布文章`；
- 已发布：`保存更新`、`下线文章`，不再显示可重复点击的 `发布文章`；
- 已下线：`保存草稿`、`恢复发布`，恢复时保留首次发布时间。

预览前的自动保存沿用同一状态语义。已发布文章预览时只能保存更新，不能把提示
写成“草稿已保存”。后台列表继续并列显示发布时间与更新时间。

专题快速编辑继续通过现有 `PATCH /api/v1/admin/news/:id` 完成，不调用发布接口，
也不改变 `published_at`。

## 公开页面与 SEO 时间

- 首页公告、News 主列表、分类页、专题页和相关推荐显示 `published_at`。
- 文章 JSON-LD 使用：
  - `datePublished = published_at`；
  - `dateModified = updated_at`。
- News Sitemap 的文章 `lastmod` 使用 `updated_at || published_at`。
- 相邻文章排序、首页最新文章排序和 News 主列表排序继续使用
  `published_at DESC, id DESC`。
- API 字段保持兼容，不删除或重命名现有 `published_at`。

## News 页面展示去重

同一页面内按以下优先级分配文章：

1. 主打文章；
2. 当前分页的普通文章列表；
3. 推荐文章；
4. 风险文章；
5. 教程文章。

低优先级区块排除已经出现在高优先级区块中的文章。普通列表保持原分页数量；
侧栏候选不足时允许少显示，不再用重复文章强行补足。服务层应一次取得略大的候选
集合后统一去重，渲染层不各自实现不同规则。

## 历史数据修复

### 修复来源优先级

1. 事故前数据库备份或 MySQL binlog 中的历史 `published_at`；
2. 可信的旧 Sitemap、页面快照或发布记录；
3. 经人工确认的文章级映射；
4. `created_at` 只能作为人工判断依据，不能批量直接替代发布日期。

重点检查 2026-07-30 和 2026-07-05 两个高度集中的时间簇，但不因时间集中就自动
认定为错误。没有可靠依据的记录保持原值并列入待确认清单。

### 执行方式

提供仓库内受控修复脚本和显式映射文件：

- 默认仅 dry-run，输出文章 ID、标题、旧值、新值和来源；
- `--apply` 前要求生产数据库完整备份；
- 创建带时间戳的回滚表，保存受影响行的原始时间；
- 在单一事务中按 `id + 旧 published_at` 条件更新；
- 实际更新行数与映射数量不一致时整体回滚；
- 同一映射重复执行时不得再次修改数据；
- 不接受仅按日期范围执行的无文章 ID 批量更新。

更新时间的修复优先使用可靠历史值；缺少历史值时，将已发布文章的
`updated_at` 设置为修复后的 `published_at`，从此由真实编辑继续推进。

## 发布顺序与回滚

1. 先部署写入保护、浏览量保护和对应测试，阻止继续污染。
2. 验证生产新旧文章的发布和编辑行为。
3. 生成历史修复 dry-run 报告，由用户确认文章级映射。
4. 备份数据库并应用修复事务。
5. 清理或等待公共页面缓存失效，验收 API、SSR 和浏览器页面。

Web/API 镜像保持配对发布。代码回滚不会自动恢复已修改的数据；数据回滚使用修复
脚本创建的回滚表执行，并再次核对更新行数。

## 错误处理与安全边界

- 生产修复前必须验证目标数据库、表名和当前行值。
- 映射包含不存在文章、空日期、未来日期或发布日期早于创建依据且未获人工确认时，
  dry-run 失败且禁止 apply。
- 不在业务请求启动时自动修复历史数据。
- 不根据文章 ID、Slug 或标题猜测发布时间。
- 审计日志继续记录发布、更新和恢复发布动作；修复脚本另外输出不可变执行报告。

## 测试与验收

### 自动化测试

- 草稿首次发布会写入 `published_at`。
- 已发布文章再次调用发布服务时保留原 `published_at`。
- 下线后恢复发布仍保留原 `published_at`。
- 普通 PATCH 和专题快速编辑不改变 `published_at`。
- 浏览量增加但 `updated_at` 不变。
- 编辑内容会更新 `updated_at`。
- JSON-LD 的 `datePublished` 和 `dateModified` 使用不同的正确字段。
- Sitemap `lastmod` 使用更新时间回退发布时间。
- 首页和 News 列表仍按首次发布时间排序。
- News 页面区块去重且普通分页数量不减少。
- 修复脚本覆盖 dry-run、幂等、旧值冲突、事务回滚和回滚表恢复。

### 生产验收

- 导出修复前后 43 篇文章的时间分布和差异清单。
- 随机抽查草稿首次发布、已发布文章保存更新、下线与恢复发布。
- 核对首页、News 两页分页、分类页、专题页和文章详情日期。
- 检查页面源代码中的 JSON-LD 与 Sitemap。
- 访问文章后确认浏览量增加，而后台更新时间不变。
- 确认文章数量、Slug、内容、浏览量、分类、专题和推荐配置保持不变。

## 非目标

- 不实现完整文章版本历史。
- 不提供自动刷新首次发布时间的“重新发布”功能。
- 不改 News 的视觉风格、分页规则或推荐算法。
- 不在缺少可靠历史依据时伪造或随机分散发布日期。
