# 权威节点地区筛选设计

**日期：** 2026-08-24

## 目标

- 机场详情页只要能从最新系统订阅节点快照识别某地区，机场排行的同一地区筛选就能命中该机场。
- 榜单卡片、筛选总数、React 页面、SSR 页面和机器可读输出使用同一份地区存在性数据。
- 将全部 33 个已识别节点地区开放给用户筛选，同时避免一次性新增 22 个内容稀疏的可索引 SEO 专题页。
- 保持既有安全边界：人工地区资料只能补充家宽、原生 IP 和线路属性，不能建立地区存在性。

## 根因与同类问题

详情页通过 `PublicViewService` 读取最新 `airport_subscription_node_snapshots`，再用共享节点地区分类器从节点名称和已存地区信息计算地区及节点数。榜单筛选与榜单卡片却只读取 `airports.airport_profile_json.regions`，并把家宽、原生 IP 或线路类型非空误当成“该地区存在”。

这造成三类不一致：

1. 大象网络的最新快照包含土耳其节点，详情页显示“土耳其 · 1 节点”，但人工土耳其属性为空，因此土耳其筛选漏掉大象网络。
2. 同一逻辑会漏掉任何已自动检测、但没有人工地区属性的香港、日本、美国等节点。
3. 共享分类器能识别 33 个地区，而筛选目录只有 11 个；澳门、泰国、马来西亚、印度尼西亚等 22 个地区没有筛选入口。

支付方式、流媒体、客户端、导入方式、套餐、Telegram 和线路类型没有发现相同的数据源分叉。线路类型仍应读取管理员维护的资料，因为节点名称不足以可靠判断 IEPL、IPLC、CN2、BGP 或中转。

## 已确认的产品规则

- 系统订阅节点快照是地区存在性和节点数量的唯一权威来源。
- 没有系统快照时，机场不匹配任何地区筛选；不得回退到人工资料。
- 人工地区资料只为系统已检测到的地区补充家宽、原生 IP 和线路类型。
- 信息提示节点不得建立地区存在性。
- 地区筛选保持现有“多选任一匹配”的 OR 语义。
- 原有 11 个地区继续拥有可索引静态专题页；新增 22 个地区先提供 `noindex,follow` 查询结果页。
- 本次不改变网络覆盖评分公式、节点健康判断、报告页 14 项展示上限或线路筛选语义。

## 架构

### 1. 快照地区索引

在 `airport_subscription_node_snapshots` 增加可空的 `region_counts_json` 字段，保存该快照中每个已识别地区的节点数量，例如：

```json
{"HK": 1, "JP": 10, "TR": 1}
```

字段由后端在写入快照时生成，使用与报告页、网络覆盖评分相同的 `findNodeRegionDefinition()` 和信息节点过滤规则。调用方传入的 `node.region` 不能绕过分类器；索引始终根据后端规范化结果生成。

兼容已有数据时，仓储 `ensureSchema()` 增加字段，并只回填每个机场最新快照中尚无索引的记录。历史旧快照无需全量回填，因为详情页和榜单地区能力都采用最新快照。未来新快照通过同一条快照 `INSERT` 写入索引。

`region_counts_json` 是快照的查询投影，不是新的业务真相。节点原始记录仍保存在 `nodes_json`，分类规则仍集中在共享节点地区分类器中。

### 2. 榜单查询

`ScoreRepository.getPublicFullRankingByDate()` 关联每个机场最新订阅节点快照，并按筛选项绑定的 ISO 地区代码查询 `region_counts_json`。地区计数大于零才算匹配。

总数查询和列表查询复用同一地区条件，避免分页总数与列表不一致。没有快照、索引为空或地区计数为零时均不匹配，人工 `airport_profile_json.regions` 不参与地区存在性判断。

榜单返回的 `capabilities.regions` 也由同一 `region_counts_json` 构建；如果该地区存在，再合并管理员维护的线路、家宽和原生 IP 属性。这样筛选命中的地区也能出现在榜单卡片和机器可读数据中。

历史评分日期仍沿用现有产品语义：分数按请求日期解析，地区能力采用最新系统节点快照，与详情页当前行为一致。本次不引入快照历史回放。

### 3. 地区目录与 SEO

扩展 `AIRPORT_REGION_FILTERS`，使其覆盖共享分类器的全部 33 个地区，并为每项记录 ISO 地区代码。增加目录一致性测试，确保筛选键、代码、中文名称与 `NODE_REGION_DEFINITIONS` 一一对应，防止以后新增报告地区却忘记新增筛选入口。

每个筛选项增加是否可索引的声明：

- 现有 11 个地区保持可索引，继续生成 `/rankings/region/<slug>`、sitemap 条目和机器可读专题链接。
- 新增 22 个地区由 UI 生成 `/rankings/all?region=<key>`，SEO 决策为 `noindex,follow`，canonical 回到全量榜单。
- 直接访问新增地区的静态专题路径不应成为可索引页面。

新增地区的筛选入口和结果页面使用现有控件、响应式布局与视觉样式，不进行额外 UI 重构。

## 数据流

1. 定时任务或管理员操作抓取机场订阅并提交节点快照。
2. 后端过滤信息节点，使用共享分类器规范化每个节点地区，并写入 `nodes_json` 与 `region_counts_json`。
3. 详情页继续从最新快照生成地区能力。
4. 榜单总数、列表筛选和榜单地区标签关联同一最新快照索引。
5. React、SSR 和机器可读输出消费统一后的榜单响应。

## 兼容性与失败处理

- 数据库变更为向后兼容的可空 JSON 字段，不删除或改写 `nodes_json`、人工地区资料或历史网络覆盖运行。
- 最新快照索引回填失败时，服务启动应报告明确错误，避免在部分迁移状态下静默产生错误筛选结果。
- 无法识别的节点继续保留在快照中，但不进入任何命名地区筛选。
- 信息提示节点即使旧数据带有 `region` 值，也必须在回填时重新识别并排除。
- 旧版采集脚本只提交节点数组即可，后端负责生成地区索引，因此无需同步升级调用协议。

## 测试策略

### 红绿回归

- 最新快照包含 `TR` 节点、人工土耳其属性为空时，土耳其筛选必须命中机场，并在榜单能力中返回土耳其。
- 只有人工土耳其属性、没有快照时，土耳其筛选不得命中。
- 快照中只有信息提示节点且旧 `region` 值为 `GB` 时，不得命中英国。
- 多地区筛选保持 OR 语义，总数查询与列表查询使用相同条件。

### 目录与 SEO

- 33 个分类定义全部拥有唯一筛选键、ISO 代码和中文名称。
- 原有 11 个静态地区路径继续可索引并进入 sitemap。
- 泰国、马来西亚、澳门等新增筛选从 UI 走查询路径，并返回 `noindex,follow`。

### 兼容回归

- 线路类型仍只读取人工地区元数据。
- 支付、流媒体、客户端、导入方式、套餐和 Telegram 筛选 SQL 与结果不变。
- 详情页地区识别、报告页最多 14 个地区、网络覆盖评分及信息节点过滤测试继续通过。

### 验证命令

- 运行快照仓储、榜单仓储、共享筛选、SEO、SSR、公共视图专项测试。
- 运行完整后端测试、前后端 TypeScript 类型检查、lint、生产构建和 `git diff --check`。
- 本地启动后验证 `/rankings/region/turkey` 能命中构造的大象网络场景，并验证新增地区查询页的 canonical/robots。

## 验收标准

- 大象网络在最新快照仍含土耳其节点时能被土耳其条件筛选找到。
- 榜单返回的节点地区与详情页来自同一最新快照，不再由人工属性决定存在性。
- 全部 33 个已识别地区都有筛选入口，且新增 22 个不会自动扩张可索引专题页集合。
- 无快照或只有人工属性的机场不匹配地区筛选。
- 既有其他筛选、线路元数据、评分与报告展示行为不回归。
