# 手动地区性能任务等待设计

## 背景

管理员执行“重新采集并重算性能”时，中心测试同步完成，上海和广州任务只被排入异步队列。当前手动任务此时就标记为成功，前端立即刷新一次；地区探针约两分钟后回传，但页面不再刷新，因此管理员只能看到中心结果。

## 目标

- 手动性能任务只有在本次已派发的地区任务全部进入终态后才显示完成。
- 等待期间显示明确进度，例如“中心采集完成，地区测试 1/2”。
- 地区任务失败或超时时，手动任务显示失败，但页面仍刷新并展示已经回传的证据。
- 定时调度保持异步派发，不等待所有地区任务，避免扩大调度任务耗时。

## 方案

`PerformanceProbeDispatchService.dispatchAirport()` 在计数之外返回新建的地区任务 ID。服务新增按任务 ID 等待终态的能力，轮询 `performance_probe_jobs`，汇总 `queued`、`leased`、`completed`、`failed`、`expired` 状态。

`ManualJobService` 仅对当天的 `performance` 和包含性能阶段的 `full` 手动任务等待这些任务。等待过程中使用现有 `markRunning()` 更新进度；全部完成后才聚合、重算并标记手动任务成功。失败或超时抛出可读错误，由现有失败路径持久化。

前端继续轮询手动任务。成功和失败终态都重新加载机场仪表盘，确保已回传的地区证据立即出现。状态条沿用现有颜色和层级，不添加新控件。

## 边界与错误处理

- 没有启用地区测试或没有新建任务时，不进入等待。
- 等待只跟踪本次派发返回的精确任务 ID，不会误计入其他机场或其他批次。
- 默认最长等待 15 分钟，可通过环境变量调整；超时信息包含完成数与总数。
- `completed` 表示地区结果已被 GateRank 接受，包括 `success` 或 `partial` 运行；探针任务自身的 `failed`、`expired` 视为手动任务失败。
- 不改变“是否并入测试结果”的评分语义，也不重写历史结果。

## 验证

- 单元测试覆盖：派发结果返回任务 ID、等待进度、全部完成、失败、超时。
- 手动任务测试覆盖：完成地区等待后才标记成功，最终消息包含完成数量。
- 前端测试覆盖：手动任务成功或失败时都会重新拉取仪表盘。
- 运行后端完整测试、Python 探针测试、前端 lint、类型检查和生产构建。
