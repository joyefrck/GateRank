# 手动任务状态轮询失败自动重试设计

## 背景

机场数据工作台创建手动任务后，每 1.5 秒查询一次
`/api/v1/admin/manual-jobs/:id`。当前实现遇到一次瞬时网络错误后会停止轮询，
但仍保留任务的 `queued` 或 `running` 状态，因此页面显示 `Failed to fetch`，
同时按钮持续禁用。该状态不能说明后台任务本身失败。

## 目标

- 状态查询出现瞬时网络错误时，继续查询同一个任务。
- 查询暂时失败期间保持按钮禁用，避免重复创建任务。
- 页面明确显示“状态查询暂时失败，正在重试”，不把查询失败误报为任务失败。
- 后端返回 `succeeded` 或 `failed` 后停止轮询，并继续使用现有成功或失败提示。
- `401` 仍沿用 `apiFetch` 的登录失效处理，不改变认证流程。

## 非目标

- 不修改稳定性采集、聚合、重算或手动任务后端逻辑。
- 不引入 SSE、WebSocket 或新的后端接口。
- 不改变手动任务的并发冲突规则。

## 方案

在 `AirportDataPage` 的轮询 effect 中增加独立的轮询触发序号。
每次状态查询完成后：

1. `queued` 或 `running`：保存最新任务记录，由任务状态变化继续驱动下一次轮询。
2. `succeeded`：显示成功消息，重新加载工作台数据，并停止轮询。
3. `failed`：显示后端失败原因，并停止轮询。
4. 查询抛出异常：显示“状态查询暂时失败，正在重试：<错误>”，递增轮询触发序号，
   使 effect 在 1.5 秒后再次查询同一个任务。

轮询 effect 仍在组件卸载或依赖变化时清理定时器。重试不创建新任务，
因此不会产生重复采样。

## 错误处理

- HTTP 非成功响应继续由 `apiFetch` 转换为可读错误。
- 网络中断只影响状态展示，不改变当前任务的业务状态。
- 任务真实失败仅由后端记录的 `failed` 状态判定。
- 登录失效时 `apiFetch` 导航到登录页；页面离开后轮询随组件卸载终止。

## 测试

先增加一个失败的前端回归测试，覆盖以下序列：

1. 初始任务为 `running`。
2. 第一次状态查询抛出 `Failed to fetch`。
3. 轮询调度仍保持激活，并再次查询同一任务 ID。
4. 后续返回 `succeeded` 后停止调度。

同时运行 TypeScript 检查和现有相关测试，确认没有改变任务终态、认证和按钮禁用规则。

## 验收标准

- 单次状态查询失败后，页面自动恢复轮询，无需刷新。
- 重试期间不会重复调用创建任务接口。
- 后端任务成功或失败后，页面最终展示对应终态并恢复按钮。
- 相关回归测试与 TypeScript 检查通过。
