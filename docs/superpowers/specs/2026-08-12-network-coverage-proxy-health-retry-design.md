# 网络覆盖代理健康检查抗误判设计

## 背景

生产网络覆盖检测当前对每个节点只通过 sing-box 访问一次 `www.google.com/generate_204`。大象网络节点的 TCP 入口和代理本身均可用，但测试目标偶发 `SSL: UNEXPECTED_EOF_WHILE_READING` 时，单次请求会直接把节点标记为 `Unhealthy`，并将具体异常压缩为 `proxy_check_failed`。

## 已确认方案

- 保留现有 TCP 前置检查和每节点独立 sing-box 会话。
- 主测试地址成功时立即判定健康，不给正常节点增加额外请求。
- 主地址失败时在同一代理会话中重试，然后依次测试 Cloudflare 和 Example 两个独立 HTTPS 目标。
- 任一 HTTPS 请求成功即可证明节点具备真实代理出口；只有所有目标、所有尝试都失败才判定不健康。
- 每个目标最多尝试两次，重试间隔 250ms，避免瞬时 TLS EOF、连接重置和短暂超时造成误判。
- 失败结果保存安全且明确的错误码，如 `proxy_ssl_eof`、`proxy_connection_reset`、`proxy_http_timeout`，不保存目标 URL、节点密钥或原始异常文本。

## 边界

- 不修改节点解析、地区识别、N 评分公式、数据库结构或历史记录。
- 不把 TCP 可连接直接当成健康；仍必须至少完成一次真实代理 HTTPS 请求。
- 不在所有目标均失败时放宽健康判定。

## 验证

- 主目标首次成功时只发起一次请求。
- 主目标发生 TLS EOF 后，重试或备用目标成功时节点保持健康。
- 全部尝试失败时节点为不健康，并输出精确安全错误码。
- 网络覆盖采集正确保留精确错误码。
- 运行 Python 定向测试、全部采集脚本测试、后端全量测试、类型检查、构建和生产无写库节点复测。
